# Apple Compliance delivery research

This is a source-reviewed research report for original plugin design. The optional local research accelerator was absent; no installer, clone, upstream execution, automatic research PASS or verified_claims.json is claimed. Only read-only public source and documentation retrieval was performed. The directory arm had no curated intent match and malformed indexed dates, so it was not freshness evidence. Independent GitHub queries and pinned implementation files are retained.

## Supported design observations

- **clm_comp_delivery_states**: The inspected Apple, Expo and release-tool sources treat build upload, processing, review submission and public release as separate workflow concerns. Sources: src_delivery_upload_builds, src_delivery_submit_review, src_delivery_release_options, src_delivery_eas_submit_ios, src_comp_delivery_code_004.
- **clm_comp_delivery_recovery**: The inspected release implementations re-resolve target identity and current submission state rather than treating a local checkpoint or retry as proof of completion. Sources: src_comp_delivery_code_012, src_comp_delivery_code_004.
- **clm_comp_delivery_auth**: Apple administration tooling distinguishes credential roles and operation-specific capabilities, so a workflow needs a resolved account and authorization lane. Sources: src_delivery_asc_roles, src_delivery_api_token, src_delivery_fastlane_api, src_comp_delivery_code_039.
- **clm_comp_delivery_mac**: The inspected macOS sources separate direct distribution signing, notarization and ticket stapling from App Store review. Sources: src_delivery_developer_id, src_delivery_notarization, src_delivery_notary_custom, src_comp_delivery_code_059.
- **clm_comp_delivery_metadata**: The inspected metadata sources manage localizations and store assets separately from the compiled application binary. Sources: src_delivery_localization, src_delivery_screenshots, src_delivery_fastlane_deliver.
- **clm_comp_delivery_purchases**: The inspected commerce sources require a purchase-verification and launch-test workflow beyond installing a client SDK. Sources: src_comp_delivery_code_046, src_delivery_revenuecat_launch.

## Inspection scope and provenance

`queries.json` records separate literal, ecosystem, practitioner, specification and adjacent-tool search rungs. `discovery.json` records the candidate identities and inspected default-branch commit file changes. `source-files.json` records exact pinned URLs and content hashes; `repos/` stores retrieved files for review. README, implementation/skill, tests, dependency manifests and available CI were inspected. Test and CI existence is not execution evidence. `docs-index.json` contains only content-valid primary documents; `doc-attempts.json` retains failed/HTTP200-not-found attempts. Every source used by the claim ledger is registered in `sources.jsonl`.

The EAS root README is a symlink text blob; its actual `packages/eas-cli/README.md` was fetched explicitly. Several guessed Apple Help URLs return an HTTP200 “Page Not Found” document, which was excluded and repaired using links from current Apple pages. No such failed page supports a claim.

## Recommended capability groups

Use seven focused delivery specialists: app readiness; metadata/assets; signing/entitlements; TestFlight/builds; submission/release; rejection response; and macOS distribution. They should share one current-policy source contract and evidence packet. The detailed original outlines in `reference-card-outlines.md` provide three substantive cards per group.

Authorization is task-scoped, not a fixed new approval ceremony. Prepare-only remains local/read-only remotely; already authorized upload/submission can continue after the exact target and readiness are resolved. Tool `--confirm` is a CLI mechanism, not a requirement to ask the user again. Read current remote state after uncertainty; a completed upload does not imply processing, beta distribution, review submission, approval or release.

## Corrections and version-sensitive boundaries

- App Store Connect **Add for Review / Ready for Review** is distinct from **Submit for Review**. Items in the same submission can gate one another. Evidence: `src_delivery_submit_review`, `src_delivery_review_status`, release implementations.
- Current Apple Help routes image/video work through **Asset Library / Manage your App Store assets**. The older guessed screenshot-upload page returns a not-found document. Keep legacy CLI/metadata paths behind installed-help checks.
- App Store localization is separate from binary/Xcode localization. Store status controls which fields are editable; image approval/attachment is also a stateful process.
- Apple screenshot guidance contains forward-dated hardware/SDK requirements. A future effective date must not become a present default. Build the matrix from platform, supported devices, app SDK and current authoritative requirements; refresh it at execution time rather than hardcoding a device table in the plugin.
- `altool` deprecation for notarization must not be generalized into a statement that every App Store binary-upload use is unsupported. Read the current task-specific Apple documentation and installed help.
- Fastlane's API-auth guide restricts individual keys for some tools; current Electron notary source has version-dependent individual-key support. Treat this as an installed Xcode/tool/auth-capability check, not a universal rule copied from either guide.
- Fastlane's export-compliance examples include a false-valued declaration. That example is not evidence about the user's app. Product owner facts and applicable Apple questions determine the answer.
- Signing certificate, private key, provisioning profile, entitlements and App Store role are different inputs. A public certificate without its private key is not a usable signing identity. Do not revoke or recreate team assets as routine diagnosis.
- Direct macOS Developer ID, Hardened Runtime, notarization and stapling form a separate lane from Mac App Store sandbox/review. Electron-specific JIT entitlements are not generic native Swift defaults.
- App Store Server Library and ASC-management keys serve different purposes. Administrative private keys belong in trusted automation/backend environments, even if a Swift SDK compiles for iOS. Signed-payload verification must precede trusted commerce processing.
- SDK debug errors may include full URLs/response bodies, and upstream examples log decoded purchase payloads. Original guidance should redact task logs and retain sensitive operational details only in an appropriate protected evidence location.

## Refuted

No blanket legal or policy conclusion is asserted. A repository badge, automated precheck, uploaded build, accepted notary ticket, current CI file, or installed purchase SDK cannot establish App Store approval. A recent pushed_at value alone cannot establish default-branch file activity.
