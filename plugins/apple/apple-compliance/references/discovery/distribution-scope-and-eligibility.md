# Distribution scope, storefronts and eligibility

Apply the [operating contract](../operating-contract.md). Use the app’s actual facts, selected lane and current authoritative sources.

## Resolve the lane before applying a rule

Record publisher/account, platform, app category, storefronts/regions, distribution channel, relevant agreements/entitlements and requested action. App Store, Mac App Store, macOS Developer ID direct distribution, and iOS alternative distribution do not share one universal checklist. A current regional program may depend on eligibility and accepted terms; a source redirect to a narrow program is not proof a general rule changed.

Keep technical capability, policy eligibility, account entitlement and legal/product decision separate. A library can display an external link or call a Node backend without establishing permission to use that purchase/distribution flow. A valid signature or notary ticket is not App Store review approval. Do not copy a successful setup from another account or region as proof for this app.

## Applicability record

For a consequential rule, retain exact current Apple URL/title/section, observation date, effective date when known, selected platform/storefront/category/agreement conditions and the fact owner. Mark not applicable only with evidence and a reason; missing eligibility facts are unknown. Recheck material sources and account state before an authorized external action.

Classify the actual product: digital content/features, physical goods/services, account-based access, subscriptions, reader content, user content, regulated services and child audience where relevant. Apply the current specific rule/exception only within its stated scope. No default checkout or backend provider bypasses this review.

## Scope sequence

1. Resolve the intended distribution endpoint and exact account/app identity. Distinguish preparation, upload, beta distribution, review submission, notarization and release.
2. Inventory targeted platforms, storefronts, deployment/artifact variants and material app features. Review existing agreement/entitlement evidence without exposing credentials.
3. Check authoritative Apple sources for the selected lane and current time. Validate page identity/content, not just HTTP success or a familiar domain.
4. Route commerce/account/privacy/content/platform questions to the appropriate specialist. Keep an actual unresolved agreement/product fact assigned to its owner rather than inventing an answer.
5. Use the readiness helper only for its supported app_store or macOS developer_id profile. Other lanes need a manual profile; do not coerce them into a superficially similar channel to get a green result.
6. Carry out authorized preparation/actions with the resulting scope and record the furthest verified state. If the scope changes, reassess affected checks instead of reusing stale approval evidence.

## Failure cases

| Inference | Why it is insufficient |
| --- | --- |
| One storefront exception applies everywhere | Region/category/agreement conditions may differ |
| External link API compiles | Technical API support does not grant policy eligibility |
| Developer ID notarized | Mac App Store review and iOS distribution are separate |
| Code/entitlement copied from another app | Account/app-specific authorization and behavior remain unverified |
| Source URL redirects successfully | The new page may describe only a narrow program |
| Future announcement exists | Current effective status and transition terms still need checking |

## Evidence and handoff

Return the selected lane, supported scope, sources/conditions, observed artifact/account facts and owner decisions still needed. Keep legal assent, fees and rights claims factual and owner-supplied; do not turn this workflow into a legal certification or universal policy table. Preserve useful completed technical work while dependent eligibility decisions remain unresolved.
