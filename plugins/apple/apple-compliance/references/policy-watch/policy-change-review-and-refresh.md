# Policy change review and evidence refresh

Apply the [operating contract](../operating-contract.md). Use the app’s actual facts, selected lane and current authoritative sources.

## Trigger a targeted review

Refresh affected evidence when app behavior, SDKs, backend processing, purchases, account lifecycle, content audience, extension surfaces, storefronts, distribution channel, agreements or submission timing changes. Also review material primary-source updates before the relevant external action. Do not start an unbounded recurring monitoring service or schedule without a user request; finish the current scope and report actual follow-up ownership.

Use the existing source record and artifact revision as the baseline. Distinguish semantic policy changes from navigation, formatting or unrelated content changes. A changed hash/ETag is a signal to inspect, not proof of a new obligation. A repository update is not policy authority. Keep observation and effective dates separate throughout the review.

## Impact record

For each material change, record the old and new observed statements with precise primary sections; selected app/lane applicability; affected feature/SDK/artifact/declaration/review item; status and evidence owner; required implementation/test; and requested external stage that depends on it. Write concise original summaries instead of copying whole documents. Keep private app/reviewer data outside source snapshots and ordinary logs.

Privacy/resource changes can affect multiple surfaces: a new SDK may change manifest/signature requirements, actual collection, labels and consent flows. A commerce or account change can affect entitlement behavior, review access, metadata and current regional eligibility. Do not update one file and assume every related assertion remains true.

## Change sequence

1. Verify current primary page identity/content and the relevant conditions. Repair a failed or moved source rather than citing a successful HTTP status.
2. Establish whether the change is effective for the app's platform/storefront/channel and intended time. Leave ambiguous product/agreement facts unknown.
3. Route technical repairs to the focused specialist and product/legal declarations to the responsible owner. Preserve existing authorization; do not create needless approval ceremonies for reversible repairs.
4. Build/test affected behavior and inspect the final artifact. For declarations, reconcile source, runtime/vendor evidence and actual product facts instead of copying a sample answer.
5. Update the evidence packet's affected statuses/references and record the artifact/contract revision. Refresh material remote state before authorized submission/release actions.
6. If a prior submission exists, inspect its actual state and supported repair path. Do not cancel/recreate it or submit duplicate items just because a local checklist changed.

## Regression checks

| Change | Evidence to revisit |
| --- | --- |
| SDK or data destination changes | Actual collection, manifest/reasons, labels, consent and resource packaging |
| Account or purchase flow changes | Review access, deletion/restore, backend state and current commerce eligibility |
| New widget/intent/notification | Protected data, locked-device behavior, target resources and permissions |
| Region/channel expands | Agreements, distribution profile, storefront-specific rules and assets |
| Toolchain/artifact changes | Actual build identity, current upload requirements and affected tests |
| Submission timeout/partial repair | Current remote state and existing item/submission identity |

## Handoff and limitations

Return the semantic source change, app impact, concrete repair, exact verification and remaining owner facts. Mark a stale satisfied assertion unknown until its supporting fact is re-established. A resolved policy-change work item does not certify legal compliance or guarantee Apple acceptance, and the static readiness helper cannot authenticate the truth of references.

If monitoring was explicitly requested, use the user's chosen supported schedule/notification mechanism with bounded scope and ownership. Otherwise report a useful manual refresh trigger without inventing future activity, publishing a policy mirror or transmitting private source to upstream services.
