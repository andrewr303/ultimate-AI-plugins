# Submission handoff and authorized state transitions

Apply the [operating contract](../operating-contract.md). Use the app’s actual facts, selected lane and current authoritative sources.

## Resolve the requested endpoint

Name the exact app/team, platform, version, artifact/build and current submission. Determine whether the user wants preparation, upload, processing observation, selected beta distribution, review submission, response/appeal or public release. Carry the resolved identity and existing authority across specialist handoffs. A tool's confirm flag is a command mechanism, not a requirement to ask the user the same permission twice.

A prepare/review request does not authorize upload, invitations, price changes, review submission, public release or factual/legal assent. Complete the concrete plan, artifacts and independent checks first, then identify genuinely missing authority or product facts. A failed readiness dependency blocks its dependent action; it does not block diagnosis or unrelated already-authorized repairs.

## Handoff packet

Record selected scope/stage; source observations and current applicability; artifact identity and revision; check states/evidence owners; safe app/version/build/submission identifiers; chosen tool/credential capability; intended mutations and recovery; and actual completed steps. Keep review account secrets, API keys, tester addresses and purchase/customer payloads in protected supported operational locations, not code, ordinary logs or plugin archives.

Separate local artifact validation from remote state. Upload, processing, assigning a build, adding/readying review items, submitting, approval and release can complete independently. Tool receipt or a local checkpoint is not proof all later stages happened. Check any related digital-goods/submission items needed by the selected current lane.

## Execution sequence

1. Re-read current remote state and verify target/account before an authorized mutation. Resolve ambiguous latest-build selectors to the intended artifact rather than trusting upload order.
2. Refresh material Apple source applicability and inspect installed tool help. Do not execute a removed shortcut or infer policy eligibility from a third-party command.
3. Prepare the supported plan/dry run and readiness evidence. Distinguish an expected pre-staging missing attachment from other real blockers.
4. Execute only the stages already authorized and ready. Preserve one chosen release/review lane and an appropriate existing draft/submission.
5. After partial failure or timeout, inspect receipts and current remote state before retrying. Do not create another submission just because the first response was lost.
6. Report the furthest state actually observed and the command/service view that can verify it. Approval and public availability each require separate evidence.

## Failure matrix

| Condition | Required handoff |
| --- | --- |
| Upload accepted, build not processed | Processing remains pending; no submission claim |
| Review item added but not submitted | Record the draft/ready state, not review queue entry |
| Expired review account/backend | Preserve the blocker and repair access within scope |
| Timeout after submit/release request | Query current submission/distribution state before replay |
| Wrong bundle/build/team | Stop the dependent mutation and resolve actual identity |
| Missing owner declaration | Keep unknown; never copy an example answer to unblock the tool |

## Completion evidence

List actions performed, exact identifiers/artifacts, observed state, checks and remaining blockers. Do not expose sensitive receipt fields. If the task ends at preparation, provide usable prepared output and a concrete next action. If a requested external action is authorized, carry it through available verification rather than stopping at a generic checklist. Source, CI and tool success do not themselves guarantee Apple acceptance.
