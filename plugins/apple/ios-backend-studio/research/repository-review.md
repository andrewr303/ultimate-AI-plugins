# iOS Backend Studio — pinned repository research

This is a manually supported source review for the requested plugin, not a repository recommendation in place of implementation. ## Deliverable implications

The plugin should help an existing native Swift app and an online Node.js backend share an explicit HTTP contract, auth and data lifecycle. Preserve the current app framework/database/host; choose an optional greenfield lane only from actual constraints. Widgets, Siri/App Intents and Mac/Xcode workflows need their own lifecycle/capability evidence, not a promise that a backend library grants background execution.

## Concrete safeguards for the new plugin

- A TypeScript type alias or a Hono inferred client type cannot be the only Swift interoperability contract. Keep the actual wire schema, status codes, content types, authentication contract and stable error shape explicit, and generate language-specific clients at controlled versions.
- Separate code generation from runtime HTTP transport and app behavior. A generator's build host, compiler requirement and emitted client deployment target are different constraints. Xcode target membership and build-tool trust need deliberate setup; do not default to disabling macro/plugin validation.
- Fastify source/docs compile schemas as application code and warn against arbitrary user-provided schemas. Its coercion/default/removal options can change request values; test actual wire semantics. Do not put unbounded database work inside initial validation.
- Successful transport is distinct from a successful HTTP response. The inspected TypeScript fetch client has explicit empty-body, success and error paths; Swift transport/middleware tests need equivalent app-level acceptance cases. Static generated types do not validate a server implementation by themselves.
- Retry semantics belong to the domain operation. A client cancellation does not undo a committed server write; a queue retry is not an exactly-once business side effect. Use durable domain idempotency and explicit acknowledgement, not only in-memory request IDs.
- Native credentials must use an appropriate platform storage/lifecycle decision. Do not transplant a web localStorage sample or assume every bearer token is a JWT. Server authorization remains required after token parsing and on every account/entity action.
- A sync connector's completion/ack path must follow a verified backend outcome. Distinguish transient retry from invalid/unauthorized/poisoned work. Optional managed sync should not silently replace existing Core Data/SwiftData or create a service subscription.
- Mac automation remains an optional inspected capability. Discover installed CLI help and the user's selected Xcode/scheme/UDID. Existing developer tooling can have telemetry, daemons, trust bypasses and code-signing assumptions; do not imply those tools are bundled or available.

Specific source observations requiring version/context handling:

- Generator and runtime main manifests currently declare Swift tools 6.2, while the inspected URLSession transport declares 6.1. This is not a mandate to upgrade the user's compiler. Generator README distinguishes supported build-host platforms from generated-code/runtime platforms; a macOS platform list alone does not prove Linux code generation is unsupported.
- Fastify main identifies itself as 6.0.0-alpha.5; the observed latest release is a stable v5 lane. Do not scaffold production against main by assumption.
- The OpenAPI TypeScript monorepo's latest GitHub release can refer to openapi-react-query rather than the packages the app consumes. Resolve each package's version separately.
- PowerSync's current custom checkpoint connector is explicitly alpha and its old base class is deprecated. Keep the stable existing connector contract or a verified compatible release; do not treat a new example as a universal migration.
- BullMQ main contains optional adapter/backend surfaces beyond older Redis-only assumptions; the inspected PostgreSQL test is not proof that all Redis deployment options apply to that adapter.
- MobileBuildMCP is the current canonical destination of getsentry/XcodeBuildMCP. Its README advertises runtime minima and uses internal Sentry telemetry; those claims and dependencies need installed-version checks, and the plugin must not inherit telemetry or trust-bypass choices silently.
- No framework, generator, host CLI, Xcode build, real APNs request, credential flow, database migration, remote deployment or cross-platform app was executed in this research task.

## Refuted

No factual contradiction independently established in this pass is promoted as a refuted external fact. The following inference patterns are rejected: recent push equals tested maintenance; generated types equal runtime payload validation; successful queue retry equals exactly-once external effect; a server auth library makes a public native client secret-capable; an MCP package's presence establishes a working Apple toolchain. Source instructions and installation examples are not user authorization.
