# Local Node/native contract kit

A small runnable contract demonstration, using Node built-ins with no dependency install. It keeps one JSON shape, one OpenAPI document and shared fixtures across a Node producer and a Swift wire adapter. It is not a production backend, an authentication implementation or durable idempotency.

Read the [operating contract](../../references/operating-contract.md), [authentication workflow](../../skills/backend-auth/SKILL.md) and [background/reconciliation workflow](../../skills/backend-background/SKILL.md). The [source registry](../../research/sources/sources.jsonl) records the broader protocol/platform research. The [OpenAPI specification](https://spec.openapis.org/oas/v3.1.0) and [Node HTTP reference](https://nodejs.org/docs/latest-v22.x/api/http.html) define the formats/APIs used here; this example's domain shape and limits are deliberate local choices.

## Run the checks

Use Node 22 or newer. From this directory:

```bash
node --test test/server.test.mjs
```

The tests create their own ephemeral servers on `127.0.0.1`, perform real HTTP requests and close only those servers. No provider, cloud account, model service, API key or dependency installation is used.

For an opt-in manual server:

```bash
node server.mjs --port 8787
```

Use `--port 0` to select an available ephemeral port and read the printed address. Importing `server.mjs` or calling its factory never binds a socket. The manual server binds loopback only. `GET /health` returns `{ "status": "ok" }`; protected routes deny requests because no real authentication adapter is configured. Stop the process you started when finished. The local HTTP endpoint is a developer demonstration, not a reason to weaken ATS/TLS for a deployed iOS app.

## Wire behavior

| Surface | Contract |
| --- | --- |
| `POST /v1/items` | Verified app account, `Idempotency-Key`, UTF-8 `application/json`, body containing only `title` |
| `GET /v1/items/{id}` | Verified app account; another account sees the same missing-resource error as an absent ID |
| Item response | String `id`, exact accepted Unicode `title`, canonical UTC `createdAt`, string `revision` |
| Error response | `{ "error": { "code", "message" }, "requestId" }`; `X-Request-ID` matches the body |
| Same account/key/payload | Replays the original body/status with `Idempotency-Replayed: true` |
| Same account/key/different valid payload | `409 idempotency_conflict` |
| Same key/different verified account | Independent operation |
| Health | Process liveness only; no claim of database/provider readiness |

See [openapi.json](openapi.json), [item fixture](fixtures/item.json) and [error fixture](fixtures/invalid-request.json). The OpenAPI document describes the intended bearer-session adapter boundary; the default demo verifies no bearer token and denies protected requests. Change that declaration if integrating an existing non-bearer session mechanism. The synthetic header-based account adapter exists only in tests and must never become production authentication.

Generated types are not runtime validation. `server.mjs` validates incoming bytes, JSON shape and title values, then checks an authorized account before the domain operation. OpenAPI can express common shape/bounds; the Unicode-scalar rule is also stated in its description and extension. It does not manufacture a complete generated client or automatically verify every third-party response.

## Text, identity and timestamp decisions

Titles contain 1–80 Unicode scalar values with some non-whitespace content. The server preserves accepted spaces and Unicode representation: no hidden trim, normalization or truncation. It rejects invalid UTF-8 and lone surrogate escapes. JavaScript `[...title].length` and Swift `title.unicodeScalars.count` match this choice; JavaScript UTF-16 `.length` and Swift grapheme-cluster `String.count` do not generally match it.

IDs and revisions are strings so clients do not accidentally change their meaning through numeric precision/coercion. This create/read-only demonstration emits revision `"1"`. Timestamps are generated by the server's injected clock and emitted as UTC text with millisecond precision. [WireShape.swift](WireShape.swift) deliberately retains the wire string before any domain date parsing. That Swift file is an uncompiled fragment to adapt into the actual client target, not a standalone compiled app or a runtime result.

## Authentication and storage seams

`createContractServer(options)` exports an HTTP server factory. A caller must explicitly inject `authenticate(request, { signal })`, returning a **server-verified** `{ accountId }` or `null`. The default trusts no bearer string, fake account header, body field or query parameter. Keep the account/tenant mapping inside the actual application's verifier and resource authorization. Adapter failure/deadline returns an unavailable error and never grants access. A configured adapter must respect the abort signal and bound its own resources; this is not a sandbox for arbitrary adapter code.

Other testable seams are `now`, `newId` and `newRequestId`. Optional trusted configuration bounds are `maxBodyBytes`, `maxRecords`, `bodyTimeoutMs` and `authTimeoutMs`. Defaults bound retained body bytes to 4096, stored records/receipts to 1000, and body/auth waits to 5 seconds each. Transport/parser failures before the application handler can have Node-native behavior, rather than this application's JSON envelope.

## What the idempotency test does and does not prove

The receipt is keyed by a serialized `(verified account, idempotency key)` pair and the validated payload. Check/create/receipt commit is synchronous and contains no `await`, so concurrent requests handled by **this one process while it stays alive** share one effect. Tests prove same-key concurrent requests create one item, changed payloads conflict and different accounts remain separate.

The maps disappear on restart and are not shared by multiple workers. They have no durable expiry, recovery, distributed locking or transaction implementation. Before adopting the pattern in a real service, use the application's durable database with an atomic uniqueness/transaction design covering account, operation key, request fingerprint, domain write and retained response. Define retention, retries, uncertain completion, schema compatibility and deletion behavior. Do not claim exactly-once business effects from this in-memory example or from a request ID.

## Verification scope

The Node suite exercises actual HTTP success, stable fixtures, isolation, concurrent duplicates, payload conflicts, malformed JSON/UTF-8, unknown fields, fixed and streamed body limits, Unicode boundaries, media types, correlated errors, adapter failure/deadline and bounded-store behavior. No Swift file was compiled, and no Xcode, device, Keychain, Siri, widget, APNs, production database or live authentication flow was run here. Those remain checks in the actual project/runtime.
